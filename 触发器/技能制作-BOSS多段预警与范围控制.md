# BOSS 多段预警、范围伤害与控制：GUI 制作规范

用途：按源码中已启用的 GUI 比较同构技能，设计可复用的多段落点、预警、伤害、范围控制与清理。下列数值和技能标识只属于《一剑爆开天门》样本，不作为其他地图默认值。本文是编辑器只读追踪与作者确认的设计，不代表已实现公共模块或完成游戏、多人验证。

## 用户确认的跨地图默认规则

BOSS 技能如果没有特别说明，默认先显示清晰预警，再延迟释放技能，让玩家有时间反应和躲避；用户明确指定其他表现时按其要求。预警应让玩家看得出危险位置、范围或方向，并与实际结算对应；预警时间要结合技能范围、速度和目标地图调节，不把源码中的 0.7、0.8 或 1 秒作为所有技能的统一标准。多段技能须检查每一段出现前的提示和反应时间；持续喷火等技能也要明确预警后的持续区域和结束时机。模型层级、遮挡、可见性、掉帧和多人实战中的可读性都需在游戏中检验。

## 本轮覆盖

已读普通 BOSS `BOSSA2`、`BOSSA3`、`BOSSA5`、`BOSSA6`、`BOSSA8`、`BOSSA9`、`BOSSA11`，存档 BOSS `CundangBOSSA3`、`CundangBOSSA4`、`CundangBOSSA6`、`CundangBOSSA9`、`N5Debuff14` 的启用动作及部分嵌套；另追踪普通 BOSS `BOSSA17`、`BOSSA18`、`BOSSA19` 的主要计时器、控制和清理路径。数量代表读取的样本，不代表各触发的全部分支已经理解。

## 二次和三次捶地是同一类机制

【BOSS技能 → BOSSA9（捶地三次）】、【存档BOSS → CundangBOSSA3（捶地2次）】、【存档BOSS → CundangBOSSA6（捶地3次）】有相同的基本流程：伤害事件筛选携带相应技能的来源和正数伤害；记录 BOSS、目标与所属玩家；检查 BOSS 对象上的自身内置冷却和技能间隔；建立预警，等待后以对应玩家的伤害马甲对范围中的符合条件单位伤害；后续阶段使用周期计时器并结束时恢复 BOSS 状态。

- 三个样本的 `num` 分别为 3、2、3；应把段数作为配置，不能为两段、三段各重写一套。其他差异如特效尺寸、伤害、冷却和目标筛选也应独立配置，不要假定只改 num 就完全相同。
- 首段以当时目标坐标创建预警，约 0.8 秒后对预警位置进行范围结算；之后的落点路径会尝试枚举合格英雄并随机选择，缺少候选时有随机坐标的分支。结算时仍要根据实际代码及逆天计时器的数据传递核对预警点与伤害点一致。
- 样本可见的目标过滤为敌方、存活、英雄、非建筑；一般技能不必照搬“只伤害英雄”，应由目标地图需求决定。
- 样本伤害在释放时按 BOSS 攻击、技能倍率、类型上存储的暴击伤害和图内倍率计算；特定难度的 DEBUFF 还可放大伤害或缩短冷却。这是参考图的 BOSS 结算，不是玩家技能公共伤害公式。
- 内置冷却和跨技能最低间隔是两个用途；作者已确认后者用于限制 BOSS 技能同时施放、控制玩家压力。样本代码把两个状态键放在 BOSS 身上并分别计时。实作时需检查同一单位多个技能的并发及旧计时器清理对新状态的影响。

## 多方向、多落点与共享命中

【存档BOSS → CundangBOSSA9（前方多方向圈炸）】启用的 GUI 将 `num1=3` 作为方向数，`num2=5` 作为每个方向的落点数、偏移角度40度；嵌套循环按方向和距离生成预警点，0.8 秒后按相同几何方法重复计算落点并枚举伤害。距离步长为 420，检测半径为 350。伤害循环在一次延时动作内创建共同单位组，合格敌人伤害前加入组，结束后销毁，因此一轮中重叠落点不会重复伤害同一目标。

可复用的结构是：方向配置 → 每方向落点配置 → 预警 → 延迟 → 按同一坐标规则结算 → 根据需求进行每轮或每个落点去重 → 清理。是否允许落点重复伤害由具体技能确定：另一技能允许不同落点独立命中时，不能照搬本样本的整轮共享单位组。预警和结算的角度、距离、目标坐标快照及模型朝向应一起核对。

进一步追踪该技能：方向基准是伤害来源指向受伤目标的角度，三个方向依次为基准、基准＋40°、基准－40°；每方向第 1～5 个落点距离释放位置分别为 420、840、1260、1680、2100。预警和延时伤害均按同一循环规则计算，结算使用释放时记录的起点和方向，不会因为目标在预警期间移动而自动追踪。目标筛选为施法者的敌方、存活且非建筑；单位组在三条方向和全部落点之间共享，筛选通过后先记入组再给伤害。是否应追踪目标、每轮去重还是每点去重，应由新需求决定。该方向数为奇数；扩展偶数数量时应明确是居中对称还是包含正前方，再设计公式，不能机械照搬。

延时结算回调中可见销毁单位组，但这一单次计时器分支未见显式 `YDWETimerStartFlush`；是否由逆天接口自动释放需查接口实现或隔离测试，不能据此断言计时器一定泄漏或一定清理。对新模块要核对每种结束路径的计时器契约。

## 直线冲击波与持续喷火的预警

- 【存档BOSS → CundangBOSSA7（冲击波）】和【CundangBOSSA8（冲击波）】分别配置3道和4道、角度参数40度；启用 GUI 先画对应方向的预警，0.8秒后发射，投射物周期0.02秒、每步30，终点播放死亡动作并延迟移除，结束时还处理命中组和计时器。两者是数量可配置复用的同类技能，但角度排布、命中组生命周期等仍需逐项检查，不能因数量改变就假设偶数方向必然左右对称。
- 【BOSS技能 → BOSSA12（喷火）】先显示前方多个方向的预警，0.7秒后进入持续发射阶段：0.1秒的周期持续生成火焰，每个火焰再由0.02秒周期移动并检测命中，单个火焰建立自己的命中组、结束后清理；施法结束时解除 BOSS 的暂停。用户要求的预警不等于整个持续期间只能命中一次：每次火焰与整轮能否重复命中应按技能需求定义。
- 【BOSS技能 → BOSSA102（天门直线）】展示直线预警后，0.8秒启动移动伤害；【存档BOSS → CundangBOSSD3（圆圈爆炸）】展示圆圈后1秒进行范围结算。形状不同可以共用“预警—延迟—释放”思路，但具体预警、目标位置、伤害范围和结束条件应匹配各技能。

## 灾厄之眼：单道去重，不同方向可重复命中

【存档BOSS → zzzz1（灾厄之眼）】用伤害事件筛选来源技能和正伤害，再按 BOSS 对象处理冷却。当前可见分支按狂暴状态配置方向数和伤害参数：普通 `num=1`、狂暴 `num=3`、二次狂暴 `num=5`；方向以基准、正负35°、正负70°排列。每个方向先创建线形预警，约1秒后建立该方向的伤害表现，并沿直线9个采样点枚举 300 范围目标，把尚未记录的合格敌人加入该次组，再遍历组给伤害。上述具体参数是本图样本，技能伤害模式与 BOSS 增益均须按目标图核对。

作者确认：不同方向的伤害分别结算，英雄处于两道重叠区域时可受两次伤害；同一道由多个采样圆组成，已读分支通过该道的组防止同一道重复计入。实现时应按每一道预警/伤害实例独立保存方向、伤害和命中组，不要把所有方向的组错误地合并成一轮共享组；如果新技能明确要求整轮只命中一次，则另选共享策略。多方向的预警与伤害轴线、模型大小及延迟仍需游戏中检查。

该分支在每个延时回调中创建 `dwz`，只在局部“运行次数”达到 `num` 的分支看到 `DestroyGroup`，并未在该回调中看到显式计时器清理；逆天计时器回调的局部数据、次数共享和资源释放语义仍未证实，不能断言各组一定正确清理，也不能仅据此宣称已在游戏复现泄漏。新实现应让每个方向负责销毁自己的组及计时器；若使用共享对象，需明确最后使用者并验证延迟回调交错、BOSS死亡和玩家退出的路径。预警单位本身有1.6秒移除动作，与伤害特效单位的限时生命是两种独立资源。

## 灾厄魔爪：死亡后继续的分批落点

【存档BOSS → zzzz2（灾厄魔爪）】通过正伤害事件及 BOSS 技能判断入口，读取施法者坐标、阵营伤害马甲与伤害参数。GUI 先在中心放置圆形预警，约0.8秒后启动0.1秒周期：普通状态配置落点范围0～800、落下次数80；狂暴配置0～1200、落下次数120。每次以随机方向和距离生成单独落点表现，给特效单位设置3秒限时生命，并在约2.5秒后以该落点枚举250范围的存活敌方非建筑单位伤害。每个落点独立运行，当前所见没有整轮共用的受击去重组；多个落点重叠可能分别命中同一目标，实际事件顺序需游戏验证。配置值及范围仅用于定位参考图，不应当成新地图默认值。

作者确认：BOSS 死亡后，本技能**继续生成并结算剩余落点**；不只保留已经出现的落点。当前生成周期和每个落点的延时回调未见 BOSS 存活中断判断，与该方向相符，但 BOSS 死亡后玩家、马甲和上下文是否仍有效，及暂停、移除和连锁事件实际行为还需游戏验证。制作类似持续技须在开始时保存本次实例所需的阵营、伤害、中心、剩余次数和可靠的伤害来源，避免后续读取已清空的 BOSS 数据；效果结束再清理自己的计时器和特效。

每个落点的伤害回调都能看到计时器清理，生成特效单位则使用限时生命；外层0.8秒单次计时器未见显式清理，是否自动释放仍需核对接口或实测。该技能可能同时存在大量落点和延迟回调，应分别测试较长战斗、多人并发和不同帧率，不能只看短期画面。若目标图有安全的集中调度器，可在保持每个落点的位置、时间、独立伤害与效果不变的前提下复用调度，减少重复逻辑；先验证是否与原机制等价。

## 无天：预警已发出后独立结算

【BOSS技能 → BOSSA20（无天）】以正伤害事件及来源技能筛选施法 BOSS，使用该 BOSS 身上的内置冷却和技能间隔标记；读取 BOSS 所属玩家的伤害马甲和攻击等参数。首段在 BOSS 周边枚举符合条件的敌方英雄，有候选时选一个英雄当前坐标，否则在 BOSS 附近随机一个点；先在该点建立圆圈预警，约1秒后在记录位置结算 500 范围伤害。后续为1秒周期，每轮预警后再以0.8秒单次计时器结算；周期继续分支还检查 BOSS 生命，终止时解除 BOSS 暂停并清理周期计时器。阶段数、取点、已经预警和未预警的区别及异常终止顺序仍应游戏验证。

作者确认：所有阶段都不应伤害建筑；预警已发出后，即使 BOSS 在对应延时结算前死亡，该圆圈仍应结算。当前 GUI 首次伤害检查敌对和存活、未见建筑筛选；后续周期伤害额外排除了建筑，属于可见写法与设计的差异，尚未游戏验证。已启动的单次延时伤害分支未看到 BOSS 存活检查，但目标数据、阵营、伤害马甲在 BOSS 死亡后是否有效需要实际验证；不能把 BOSS 死亡后是否继续生成新预警，与已经预警的圆圈是否结算当成同一个问题。

预警单位使用 `TX_BOSS_Quan[1]`，初始化对应 `e01D`，物编名“马甲（警告圆圈）”，含无敌、蝗虫技能；预警单元有0.9秒移除动作。结算分支另外创建特效单位并换成 `tx-170.mdx`；该模型的已读动画表只有 Birth，因此按用途决定播放后移除即可，不因缺少 Death 视为缺陷。当前两段延时回调都创建局部组及特效单位，但在已读回调中未见相应 `DestroyGroup`、特效单位移除动作，后续回调也未见显式计时器清理；初始化和单位属性也不能单独证明会自动释放。需查完整接口/其他清理及隔离游戏测试，不能凭静态结构直接断言已经泄漏或自动清理。新技能要对每个已发出预警单独保存位置、伤害、马甲和生命周期，并为预警、伤害特效、单位组和计时器分别设计完成及中断清理。

## 预警中心与实际伤害中心

【BOSS技能 → BOSSA103（自身大范围）】由正伤害事件检查伤害来源的指定技能，通过 BOSS 单位上的技能冷却和共享施法间隔决定是否启动；读取 BOSS 与受攻击目标在触发时的坐标，创建圆形预警，约2秒后执行范围伤害。预警及后续特效使用当时记录的 BOSS 坐标，当前 GUI 的伤害枚举则使用当时记录的受击目标坐标；作者确认设计是**伤害以 BOSS 预警圈的位置为中心**。这是静态动作与设计存在差异，尚未游戏复现，也没有修改源码。

制作同类技能时，在预警创建时明确保存中心和半径，后续伤害使用约定的同一组坐标；若技能设计为跟踪移动目标，则必须在预警阶段同步表现，并单独明确取消、BOSS 移动或死亡后的结算规则。预警显示范围和伤害判定半径也需结合模型尺寸核验，不能只检查它们都叫“圆圈”。

## 相同爆炸机制的攻击与受伤入口

【存档BOSS → zzzz3（圆圈爆炸）】及【zzzz4（受伤圆圈爆炸）】都在正伤害事件上检查同一技能标识，但主体不同：zzzz3 从伤害来源取 BOSS、以本次受击单位的位置作为落点；zzzz4 从受伤单位取 BOSS，再由攻击来源所属玩家读取绑定英雄，把英雄位置作为落点。两条均在 BOSS 单位上读取并写入相同的“内置CD中”和“无法释放CD中”字段，因此可见结构是同一只 BOSS 的两个入口共同受这些标记约束；不同 BOSS 的数据仍按各自单位区分。事件是否先后发生、哪些来源能进入受伤分支及空绑定英雄时的表现需要游戏验证。

两条分支均先记录落点、生成圆圈预警，约0.8秒后解除施法暂停并创建第一段视觉，再约0.6秒后在记录位置枚举600范围内符合敌对、存活和非建筑条件的单位，使用 BOSS 阵营的伤害马甲给伤害，并为受击者创建临时施法单位、添加 A02K 并下达风暴之锤命令。预警单位设置1秒后移除，后续视觉持续与伤害发生时间不同；是否仍有足够清晰的提示应在游戏中观察。物编中 A02K 是风暴之锤模板，能确认有魔法效果等自定义字段，但仅凭修改列表不能得出其所有继承字段、眩晕时间或附带伤害；目标选择、魔免、附带原生伤害、控制重叠和临时单位清理都应核对。

做同类技能可复用预警、延迟与范围结算，但应分别传入正确的 BOSS、被攻击单位或攻击者绑定英雄、伤害来源和固定/跟随的落点；不能因动画一致就把攻击触发与受伤触发当成同一个事件。玩家没有绑定英雄、BOSS死亡、延迟期间目标移动及多个监听器先后均需单独定义和测试。

## 范围控制与多人重叠

【BOSS技能 → BOSSA17（时光之门）】在英雄位置创建预警与持续特效；延迟后开始 0.1 秒周期，在范围内暂停符合条件的敌人并加入单位组，结束时遍历组恢复、销毁组并移除特效马甲。作者确认设计希望控制范围跟随英雄脚下的特效；本次 GUI 中被枚举的范围中心读取的是此前保存的 BOSS 坐标，与特效所在的英雄坐标可能不同，属于静态差异，尚未游戏验证，也未修改地图。

做类似技能时，应明确“取英雄位置一次作为固定落点”还是“持续跟随移动中的英雄”，不能仅凭作者这次回答替后续需求推断；预警、伤害和控制需共享约定中心。多人或多只 BOSS 重叠控制同一目标时，各实例直接暂停和解除暂停可能相互干扰；需按目标图实现可验证的状态归属、重叠解除与单位死亡/移除处理，而不是任一计时器结束都无条件解除全部控制。

【BOSS技能 → BOSSA18（剑影留痕）】包含周期预警、延时落点伤害和结束时单位组清理；【BOSS技能 → BOSSA19（树界）】包含范围伤害、暂停、后续周期伤害与解除暂停。这些只确认了已读的主要结构，伤害间隔、组归属及多个实例交错仍需继续追踪和实测。

进一步对照【BOSSA18】：每轮先按记录方向给出警告，再通过 0.5 秒单次计时器执行该轮伤害；伤害阶段沿同一方向设置 8 个距离逐步增加的采样点，使用该轮新建的命中组，伤害前先将目标入组，因此同一轮重叠检测不会反复命中；每轮结束清空并销毁本轮组。不同轮分别建立组，能否因事件、目标状态或其他条件实际重复命中仍需游戏验证。预警生成节奏为 0.3 秒，后一轮可在前一轮 0.5 秒延时结束前开始，因此实现时不能让不同轮复用会被其他回调覆盖的角度或组；逆天计时器的局部传参须在当前版本验证。

【BOSSA19 → 树界】在记录的目标坐标周围创建多组树形视觉，延时后以该位置为中心枚举 850 范围的合格敌人，给一次伤害、加入该次组并暂停；之后 1 秒周期计时器遍历这组单位，当前可见的继续分支计数小于 2 时，对存活者每次给予初次伤害的 1/5，结束分支解除组内单位暂停并销毁组。BOSS 自身在施法阶段暂停，进入后续处理时解除。对象移动后仍由已记录的单位组处理，不能将其误写为每轮重新按位置筛选。多次控制叠加、单位中途死亡或被移除、BOSS 提前死亡以及逆天传参仍须另行验证；不同控制来源不能随意互相解除。

## 受伤触发的自定义无敌

【BOSS技能 → BOSSA7（本多无敌）】从 JY 伤害事件读取受伤单位作为 BOSS，确认其拥有指定技能并且事件伤害大于0；技能内置冷却和共享施法间隔均未占用时，将触发当次事件伤害设为0，在 BOSS 本体上写入“无敌中”，显示护盾特效并启动计时。该分支约0.5秒后解除 BOSS 施法暂停，约3.5秒后将“无敌中”清零并销毁护盾特效。内置 CD 与其他技能之间的间隔分别有倒计时，且受本图 DEBUFF11 缩短影响。

关联消费端【中心系统 → jianshang_Guai → 怪物】读取受伤怪物的“无敌中”，符合条件则把局部最终伤害设为0，再写回事件伤害。此受伤入口本身要求事件伤害大于0.10且目标不属于玩家1盟友；其怪物分组里有其他技能分支位于无敌状态判断之前，因此是否在无敌期间仍产生前置反应，须结合各条件和监听器顺序验证。无敌是与伤害处理配合的自定义状态，不应仅复制盾牌外观就当作无敌，也不能在新地图假定其所有伤害都经过同一监听器。触发技能的那一下、持续期间的其他伤害、标记清除后的伤害和监听器先后必须分别实测。重叠无敌应检查状态是否由旧计时器提前清除，按目标图设计实例或延长规则。

本次只读 GUI 在该技能中看到创建 `dwz` 单位组，但未在此触发器的启用动作中找到对它的使用或销毁；是否通过其他机制处理仍需检查，不能只凭此断言游戏发生泄漏。新技能应只创建实际需要的组，并为每个组和计时器明确清理责任。

## 面向制作的检查

1. 根据需求选择触发时机：伤害来源是 BOSS、BOSS 自身受伤，或其他事件；不要把所有 JY 伤害事件都按同一主客体解释。
2. 确定阶段数、每段预警和伤害位置、延迟、预警模型和大小、目标过滤、伤害马甲及去重范围；相同机制参数化，行为不同则保留单独策略。
3. 每次释放、每个计时器和控制实例要有明确数据归属；注意逆天局部变量/数组的传递范围，不把本地图的函数、字符串键和技能 rawcode 当作其他地图已有接口。
4. 每个正常结束、施法者死亡、目标移除、提前中断和重叠结束路径，分别核对暂停恢复、计时器、单位组、预警/特效马甲及临时数据的清理。单次计时器在某些已读路径中未看见显式 `YDWETimerStartFlush`，是否由接口自动释放需核查函数实现或实测，不能仅此断言已泄漏或已安全。
5. GUI 读回、保存编译、游戏单人和多人重叠是不同验收层次；本次只读学习不等于均已通过。
