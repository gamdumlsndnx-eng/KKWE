# 中心伤害计算：技能接入、力量倍率和目标结算

用途：以后为 KKWE 目标图制作“造成某属性百分比伤害”的可编辑 GUI 技能时，理解需要哪些输入、输出与后续事件。依据用户《一剑爆开天门》源码备份中当前启用 GUI 的只读核对，以及作者明确的设计答复。字段、rawcode 和具体增益属于参考图；目标图必须先确认对应属性、模块、伤害事件和马甲。静态流程与作者意图有差异时分开记录，不能直接把当前源码当作已经符合设计。

## 从技能到目标：三层责任

1. **技能负责上下文与参数。** 选定玩家、目标、技能伤害来源，决定物理/法术计算模式、系数、伤害类型A/B 和具体效果；使用逆天局部变量与运行触发器显式传参。玩家属性由玩家对象读取；目标类型相关增伤需要传入实际怪物。不要假定计算模块凭玩家自动知道本次目标。
2. **`Dislpay_Sh` 负责计算一次伤害。** 输入 `s`、`玩家`、`伤害参数`、`伤害类型A/B`，需要目标相关判断时传入 `怪物`；输出写入 `ShangHai[玩家编号]`，同时技暴阶段使用 `ShangHai_BaoJi[玩家编号]`。调用后将此次需要的数值保存到技能自己的局部实例，延时/多目标实例不要一直依赖同一玩家的共享槽位。调用内部可能嵌套技暴传输，不能只靠“调用后再读全局标记”就断言重入安全。
3. **技能使用对应马甲给目标伤害。** 目标受伤事件中的 `jianshang_Guai` 对满足入口条件的怪物进一步处理受伤加深、免伤、闪避等，并回写事件伤害；死亡和奖励另有后续入口。该入口可见事件伤害必须大于0.10，并排除玩家1的盟友目标，不能把它当作所有伤害都会走到的通用结算。其伤害记录分组采用最终伤害与目标当前生命的较小值计入玩家总伤害/DPS 的相关分支；因此超出剩余生命的计算数值不一定全计入伤害统计。计算模块的输出不是已经扣到目标生命上的最终实测结果。英雄原始伤害、分裂单位3模拟普攻、分裂单位2多重箭和普通技能分裂单位要按目标图真实设计区分，以免技能伤害反向触发普攻分支。

参考链位置：【中心系统 → shanghai（英英雄+法宝伤害）→ 英雄伤害】检查 e002 模拟英雄来源后，按 R/SR、SSR、UR 通过逆天运行 `shanghai2/3/4`；【中心系统 → shanghai2 → BMJR+1 玄铁剑 → 伤害】选择 `s=3` 或 `s=13`，分别以 `1.00` 和 `1.20` 调用两次中心计算，传入玩家、伤害类型A=2、B=1 和怪物，每次取得 `ShangHai[id]` 保存为各自局部伤害，再由玩家的 `分裂单位` 给目标伤害。原图所读 `UnitDamageTarget` 使用的引擎攻击/伤害类型参数必须与目标图伤害系统一起核对；不能把 `s=13` 自动等同于某个原生 `DamageType`。作者确认对 BOSS 的增伤应针对**每个受击目标**分别判断；玄铁剑当前可见流程先以触发时的怪物算伤害、再复用于其他目标，若目标类型不同，可能与此意图不符，仍需完整路径和游戏核对，未改源码。

## 示例：300% 力量

技能初始化要与英雄创建衔接。【英雄系统 → hero_Set（创建英雄）→ 初始】先建立英雄类型与天赋技能的映射；循环处理正在游戏的人类玩家时，创建英雄、将英雄绑定到该玩家，再根据英雄类型读取并添加天赋技能，同时把天赋技能绑定到玩家，随后通过公共属性模块增加初始属性。新地图应先确认玩家槽位、英雄创建/更换时机、物编技能模板和绑定字段，再安排伤害模块及技能入口；不能只复制后续伤害触发器，假定英雄、技能和属性已经就绪。本图的槽位数量、初始值和具体映射不是其他地图的默认值。英雄更换、离线和重新绑定等流程未在本次完整核实。

先建立属性来源：参考图【英雄系统 → hero_Set（创建英雄）→ 初始】向 `Display_ShuXing` 传 `s=1`、玩家及力量/敏捷/智力各 `100.00` 和升级三围各 `10.00`。`Display_ShuXing` 的可见加法分支按玩家读取原有“力量”等值并加传入量；`shuxing1` 再每秒遍历玩家，计算并保存带增幅的 `力量1` 等。创建英雄时还把玩家原有“技暴伤害”加 `1.50`。这些都是**增加量**，不能在未核对初始值时当作直接覆盖的最终数值。目标地图需要自己的初始化及刷新机制；属性变化与一次技能计算可能发生在不同更新时间，具体即时刷新和跨玩家顺序仍需实测。

若新需求明确“300% 力量的物理技能伤害”，且目标图已具备与参考图兼容的中心模块，可传 `s=3`、`伤害参数=3.00`、`玩家=施放者所属玩家`、`怪物=实际目标`，并按技能定义设定 A/B；法术使用 `s=13`。A=2 表示参与该模块的技能暴击分支；B=1 是周期技能、B=2 是被动技能。A/B 与 `s` 是不同维度，参考图的分类不应未经核实硬套其他图。`伤害参数=0` 在当前模块会被改为 1，不应拿它表达零伤害。

参考图 `s=3` 的基础分支为局部力量 × `(1+物理伤害1)` × `(1+全伤害1)` × 参数；`s=13` 对应法术伤害1。之后还依次经过周期或被动技能加成、力敏智技能加成、目标类型加成、特定技能/装备增益、波动、技暴、特定状态和最终伤害等启用分组。`s=1/11` 的攻击力基数分支当前无论 A 类别都乘 `普攻伤害1`；作者明确设计意图是**普攻加成仅影响普通攻击**，即使用攻击力作为基数的技能也不应自动吃普攻加成。当前可见分支与此意图存在待核验差异，新技能不要照搬该行为。

示例假设仅有：力量基数 100、参数 3、物理伤害1=20%、全伤害1=10%、被动技能伤害=50%、力量技能伤害=20%，A=2、B=2，不触发技暴及其他分组。当前启用 GUI 在两个不同位置分别乘一次被动技能伤害，作者明确确认**乘两次**是本图设计：`100 × 3 × 1.2 × 1.1 × 1.5 × 1.2 × 1.5 = 1069.2`，这是进入目标受伤处理之前的计算示例，不是最终游戏伤害。计算使用的力量基数是否应含力量增幅，见下方作者确认与当前动作的差异；示例只为说明各环节，不能作为其他地图默认规则。

## 实际输出、暴击及作者确认的差异

- **血屠的生命附加伤害与目标增伤顺序**：【一些触发传输 → Dislpay_Sh → BMJSSR+2】在拥有该技能且伤害类型 A=2 时，将英雄最大生命的 15% 作为额外伤害基数，根据 s 分支乘物理或法术伤害系数、全伤害系数及当前局部“普攻伤害”系数，再加进本次局部伤害；这在已读分支中是合并进计算结果，并非已证明另外发起一次伤害事件。随后才进入技暴等后续分组。作者此前确认普攻加成只影响普通攻击；此处局部“普攻伤害”由 `1 + 玩家普攻伤害1` 得到，即使 A=2 也参与附加生命伤害的计算，与上述设计存在待核验差异，不应将此疑点照搬到新技能。
- 本计算器在加上血屠生命伤害之前已执行【对一些BOSS伤害加成】；因此按当前可见顺序，前面已完成的 BOSS 加成不会自动作用到后加的那部分生命伤害。作者确认附加生命伤害也应享受对应目标的 BOSS 增伤。设计新技能时，应先保留本次释放共同的暴击判定、伤害和附加项，再针对每个实际受击目标应用应有的 BOSS 修正，避免重复随机技暴；具体属性增益顺序和目标图接口需先核对。当前结论是静态顺序与作者意图对照，尚未进行游戏实测或修改源码。
- 血屠物品 `I055` 和旧分组写“释放技能加 100 最大生命”，作者后来明确更正：实测认为不平衡，**现在不需要增加该生命值**，不要按旧描述把它加回。作者确认每秒周期伤害仍应存在、一次持续 3 秒；首次伤害是立即还是延迟一秒，以及不同实例重叠方式未确认，不能擅自指定。相关技能状态和物编不应只依据名称或旧说明来实现。
- 伤害计算开头把玩家 `力量1/敏捷1/智力1` 读入局部，但后面的“主属性”分组又将局部三项覆盖为玩家 `力量/敏捷/智力`，`s=3/13` 随后使用覆盖后的局部力量。属性刷新 `shuxing1 → 各项增幅 → 力量` 把 `力量1` 算为力量加力量增幅贡献并取整。作者确认：力量100、力量增幅50%时，300%力量技能应以增幅后的150为基数。当前可见覆盖动作与此设计可能不一致；仍需核对其他属性更新路径和游戏数值，未改源码。新图应使用作者指定的有效属性接口，不能照搬疑似覆盖。
- `伤害类型B=2` 且“被动技能伤害”大于0时，【主动技能伤害或被动技能伤害】和紧随其后的【力敏智技能伤害加成】各乘一次 `1+被动技能伤害`；作者明确说本图就是乘两次。不能擅自去重，也不能未经新地图要求把双乘当成通用公式。
- 力量/敏捷/智力技能伤害加成的可见分支要求 B=2 并匹配各自 s；例如力量匹配 3/13。B=1 的可见分支另按周期技能伤害处理。是否应让其他类别享有同类加成，应按目标地图规则处理。
- 技暴分组先将 `ShangHai_BaoJi[id]` 清零，生成1～100随机整数；A=2 且随机数不大于 `R2I(技暴几率 × 100)` 时设标记1，把伤害直接乘以玩家 `技暴伤害`，并运行 `display_Jibao`。`hero_Set → 初始` 可见玩家技暴伤害在原值上加1.50；从零开始是1.50倍，不能把该字段再当作必定需要 `1+字段` 的增幅。后续装备/技能还可改变它。对技暴套装、同玩家嵌套输出和显示标记需要进一步核对。
- FQHC36 物理波动和 FQHC37 法术波动，作者确认应各由36、37分别控制；当前法术分组所读状态键仍构造 FQHC36，与设计存在待核验差异。先保留问题，不直接改图。
- FQA84 分组说明仍写“首次技能暴击增伤”，但启用条件为拥有 FQA84 且伤害类型A=1，乘1.5；作者确认当前设计按普攻相关条件增伤50%。不要按旧分组文字擅自加入“首次”或技暴条件。
- 范围技能面向不同目标：作者确认每个受击目标独立判断自身是否符合狩猎、进攻、境界 BOSS 等相应增伤条件；本次示例中，同一次释放对不同目标**共享一次技暴判定**。因此可把一次施放的基础伤害和暴击结果单独保存，命中每个目标时再按该目标应用相应增伤；不要把原目标的 BOSS 类型套给全部单位，也不要为了逐目标增伤把同一释放的技暴重新随机。其他技能若有不同要求仍按其设计确定。
- 嵌套示例：【一些触发传输 → display_Jibao（技暴传输）→ FQA148 → 伤害】根据玩家伤害类型选择中心计算模式，传入玩家、参数1.00、A=2、B=2，但可见传参未显式给 `怪物`；后续再沿路径枚举目标。玩家足以读取该玩家的属性，并不自动说明计算器已经知道每个后续目标。目标专属加成应在目标已知时处理，局部变量实际继承及此分支的 BOSS 增伤须继续核实；不得仅凭这一处就断定游戏结果。
- FQA148 也是共享输出重入的具体案例：外层中心计算命中技暴后设置 `ShangHai_BaoJi[id]=1` 并运行 `display_Jibao`；满足 FQA148 条件时先设置它自身冷却，再嵌套运行一次中心计算。内层又会先重置同一个玩家的暴击标记；外层返回前会写入自己的 `ShangHai[id]`，但可见动作未重新设置外层标记。因此同玩家外层伤害结果与最终暴击标记可能来自不同次计算；需要实际重入和显示测试，不能直接宣布已复现错误。设计新系统应让每次释放持有自己的伤害与暴击结果，且避免内层覆盖外层；先对照目标图是否已有实例级返回机制。
- BOSS 类别数据需要初始化：当前 GUI 的【进攻怪 → ALL_Set1】给 `Guai_JG_BOSS[p]` 和 `Guai_JG_BigBOSS[p]` 对应的**单位类型**写入 `是进攻BOSS=1`；【境界系统 → Jingjie_Set】给 `Guai_BOSS_JJ[p]` 的单位类型写入 `是境界BOSS=1`。计算器根据传入目标的单位类型读这些标记；仅有单位名称或外观是 BOSS，不代表目标图已有这些分类。【狩猎爬塔 → Shoulie_Set】给 `Guai_SL[p]` 的单位类型写入了 `是狩猎怪=1`、`是BOSS=1` 和 `是计时器BOSS=1`；但计算器读取的是另一键 `是狩猎BOSS`。现有 GUI 转换结果的全文检索仅在计算器发现该键的读取，尚未找到写入；不排除其他脚本或转换遗漏，实际增伤尚需验证，未修改源码。
- 作者进一步说明，`是狩猎BOSS` 应该是打错字，预期使用狩猎爬塔初始化的 `是狩猎怪`，也可能存在标记混乱。实时 GUI 核对：【狩猎爬塔 → Shoulie_Set】对 `Guai_SL[1..30]` 的单位类型设置 `是狩猎怪=1`；【狩猎爬塔 → SL1_display（狩猎出怪调用）】依据玩家狩猎等级选择 `Guai_SL[等级]` 创建怪物，扫描时同样按单位类型读取 `是狩猎怪`；【一些触发传输 → Dislpay_Sh → 对一些BOSS伤害加成】则读取 `是狩猎BOSS`。作者对是否单纯笔误仍有保留，完整外部脚本及实际伤害尚未验证；不能据此直接更改地图。新图应以目标系统中已经定义的统一键做分类，并按受击单位类型核验，不要复制这个不一致。
- 属性来源与目标类别是两组不同数据：实时 GUI 中【商城 → SC_JL → 积分道具 → SR → 其他】在拥有 `VIPJSR2`、玩家“满积分=1”或“全满=1”的任一条件成立时，将本次局部“对狩猎BOSS伤害”加 `0.03`；后续以 `s=1`、玩家及该局部值调用 `Display_ShuXing`。属性加减模块的可见正向分支把传入值加到**玩家对象**的同名属性，反向分支做减法；中心计算再读取玩家增伤，并独立检查受击**单位类型**的分类键。此处仅说明数据路径及该次启用分支，不代表商城奖励触发的调用次数、所有物品来源或游戏增伤已验证。
- 技能计算器还有 `s=-1` 自调用分支；作者明确是测试用途，不能作为正式伤害模式使用。

## 英雄创建的真正入口

【英雄系统 → hero_Set】整条触发器启用，但其自身的0秒定时事件处于禁用状态，不能由“触发器启用”推断它会自动执行。继续追调用可见：【UI【难度选择】→ UI_ND2d】接收难度同步后运行 UI_ND_dp；【UI_ND2c】接收修仙模式同步后运行 UI_ND_dp2。两条设置触发器的启用分支在各自“初始创建”中运行 hero_Set，并受本图“已选完难度”状态条件限制。此处体现“禁用一个事件但允许被其他触发调用”，不能把这条仍启用的触发器当成整条禁用备份。

本命剑的 JianXin_Set 则具有启用的2秒一次性定时事件，文字模型的 sh_Set 为启用的0秒一次性定时事件；它们和用户触发选择、英雄创建是不同入口。制作新系统时要画出初始化依赖，检查数据、物编标识、玩家状态和模块何时就绪、是否可能重复执行或先后冲突；不同初始化事件的时序及极快选择操作是否会产生问题，本次尚未游戏验证。

## 具体链路：从魔斧剑初始化到伤害显示

1. 【UI【本命剑】系统 → JianXin_Set】将魔斧剑物品 I04T 放入 BMJ_WP_2SR[1]；SR 循环为物品类型记录是本命剑、SR 分类、绑定单位类型、标识 str（BMJSR 加序号）及参数等；基础属性另在物品类型上设置。地图已有的物品池、技能状态与显示文本是不同数据，不能只复制一个物编对象就认定初始化完成。I04T 和字段名只在参考图使用。
2. 【UI【本命剑】系统 → UI1d（同步获得本命剑技能）】读取同步玩家和选项，通过物品类型拿标识，分别记录玩家技能槽的“已拥有技能”和该玩家具体本命剑的“已拥有”，并将物品属性交给属性模块。【shanghai2 → BMJSR+1】再按玩家和 BMJSR1 标识检查拥有、冷却，选择力量物理或法术模式，传玩家、参数、伤害类别及原目标给公共计算模块。初始化、获得与实际触发发生在不同触发器，其他地图须核对其绑定和接口。
3. 计算器写出玩家编号对应的 ShangHai 和技暴标记；魔斧剑读取伤害后先调用 display_TX，传 s、t、伤害、我（显示位置对应的单位）和暴击等，再由伤害马甲对枚举单位给伤害。伤害类型及输出标记的具体时序在嵌套、多玩家情况下需验证，不应把玩家共享槽当作每次施放的永久私有结果。

## 中心计算器的 s 与输出约定（参考图）

## 伤害飘字的参数与真实扣血

【伤害用特效模型显示 → display_TX（物理+法术）】通过逆天局部参数接收 s、t、伤害、我、玩家和暴击；当前启用显示分支依据传入伤害生成数字，依据 s 是否大于10选择物理/法术色系，并依据暴击选择不同样式，在“我”这个传入单位处生成文字并设置移动。参考 KKWE 的 `YDWETimerDestroyTextTag(0.80, pfwz)` 通过原生文本标签字段设置寿命，没有为每个飘字启动一个触发计时器。当前读到的启用分支中，t、玩家只有入口赋值，未见后续使用；不推断它们在关闭的旧分支或其他版本中无用途。具体数值格式、极大数值转换和动画在实际游戏中需验证。

【UI【控制台】→ tbKong（同步控制台按钮2）】按同步玩家切换该玩家的“伤害显示”，并将开关写入本图存档；【存档奖励 → JiFen_Map_Set3】依据存档恢复该字段和按钮。【display_TX】读取本地玩家对应开关决定是否生成伤害文字；显示状态不能改变同步的伤害、随机数或奖励。不同玩家开关、初始化顺序及联机运行必须在目标环境验证。收益文字另由【一些触发传输 → dispaly_pfwz】接收类型、单位和数量，不能与 display_TX 的参数混为一谈。

作者明确希望伤害飘字显示**实际扣除的生命值**。本次看到魔斧剑先把计算结果传给 display_TX，再执行伤害动作；【jianshang_Guai】对符合入口条件的事件之后还可能进行减伤、无敌、闪避等处理和回写。这里存在传入值与作者预期可能不同的静态风险，并非已实测 BUG。实现新图时应选择经实测的实际扣血结果作为显示来源，区分伤害计算值、事件修正值、原生护甲/免疫及最终生命变化；检查过量伤害、0伤害、治疗与嵌套伤害。不能未经验证就把受伤事件中的某个中间变量声称为最终扣血。

- 同样的显示顺序出现在【shuxingGuai → 中毒减血】与【shanghai2 → BMJR+1 玄铁剑】两段命中。玄铁剑沿途使用按 1.00 计算的局部“伤害1”，终点使用按 1.20 计算的“伤害2”。两处飘字都在给伤害之前传入另一个局部“伤害”，并在延时回调里读取当前的 `ShangHai_BaoJi[玩家ID]`。检查每一段的显示值、目标和暴击标记是否来自该次命中。把数字存入本次技能的局部值后再进入延时动作，还要在公共计算触发其他技能时保持外层暴击结果，见[技暴与逐日剑法调用链](技能伤害-技能暴击与FQA148调用链.md)。
- 调整显示时可保留 `display_TX` 的格式、开关和文本标签寿命，先用一条单独的伤害入口核对普通命中、减伤／免疫、过量伤害以及同一目标同一时刻的附带伤害。若采用给伤害前后读取生命之差的做法，要先确认 KKWE 游戏中该入口的给伤害动作返回时生命已更新，且能区分本次命中与嵌套伤害或即时治疗。现有排行榜的“伤害值”在回写事件之前计算，适合作为对照。参考插件的 `JYDamageEvent` 注册的是 `EVENT_UNIT_DAMAGED`，当前证据不足以把它作为扣血后的统一显示入口。

【伤害用特效模型显示 → sh_Set】虽在初始化时把数字模型路径写入键，但本次在 display_TX 里找到的读取这些模型的路径位于禁用的祖先分支；当前启用路径是文本标签显示。其他启用触发是否使用这些键仍需单独追踪，不能根据初始化存在就认定这套模型目前用于伤害飘字。

## 伤害飘字、统计与排行榜是不同模块

【中心系统 → jianshang_Guai → 每个的伤害记录】的启用入口目前要求事件伤害大于0.10、受伤单位不是玩家1盟友。该分支先经过已读的无敌和闪避等状态判断，再将本次局部“最终伤害”和目标当时生命值中较小者写入玩家“总伤害”；满足额外条件时也累加该玩家的“DPS”。随后才把局部最终伤害写回伤害事件。例：该分支中某次局部伤害为100、目标当时生命为60，统计字段使用60。事件顺序、原生减免、其他监听器和实时生命扣除是否完全一致仍须游戏验证，不能把这个静态统计值直接称作经实测的实际扣血。

【排行榜/战斗力/时间显示 → 5_miaoGet】使用玩家“总伤害”除以至少为1的全局游戏每秒计数；该每秒计数在【中心系统 → Meimiao】中递增，而 5_miaoGet 自身的启用事件是每3秒一次。这个结果是已读公式下的累计平均值，不应因名称推断成最近一秒的即时伤害。另有【UI【新的】→ DPS（DPS排行现）】读取玩家“DPS”字段做排行显示，与上面的总伤害平均值是两个用途，数字不保证相同。

作者补充：这个排行用于向玩家展示自己在四名玩家中的伤害和名次，带来直观反馈与成就感；具体是竞技排名、合作展示还是奖励依据，应按目标地图需求决定。

【进攻怪 → ChuGuai → 最后一波 → 伤害排行】运行排行显示模块；【jianshang_Guai → 每个的伤害记录】当前对“DPS”的追加同时要求排行已开启，并通过“是最终BOSS=1 或 是存档BOSS=1”的单位类型筛选。作者确认：排行榜开启期间应统计所有合格敌人的伤害，而不仅是这两类 BOSS。此处可见动作与该意图存在静态差异；还需核对其他可能的写入入口、最终阶段的实际敌人范围、玩家归属及游戏表现，未修改地图。胜利触发【地图初始化 → GameYES】也读取“DPS”字段作玩家伤害比较，因此未来调整统计范围时还应检查对胜利结算的影响，不能只改界面数字。

实现其他地图的排行榜时，先定义统计期间、合格目标、过量伤害、马甲归属、各次伤害的实际结算时点及平均/瞬时口径；浮动文字、伤害排行和胜利奖励可以共享核实过的伤害事件，但各自的口径和数据生命周期应明确。上述读回和作者意图不代表已完成编辑器保存或单人/多人测试。

## 建立新地图系统和验收

空白图不具备此参考系统时，先与目标图现有设计对齐：初始化玩家—英雄—伤害马甲绑定、提供明确的有效属性读取和必要默认值，设计计算模块的输入与每次执行输出、伤害类型及最终目标受伤处理，再逐项写成可编辑 GUI。一个只把固定数值交给马甲的触发器只是伤害传输，不是完整的属性、暴击与伤害计算系统。

验收至少区分：基础力量改变与力量增幅改变；物理/法术、自适应；B=1/2；非暴击/技暴；目标类型增益；两个玩家及同一玩家嵌套；目标受伤、死亡和奖励；输出快照和资源清理。与用户约定具体数值，比较计算中间值与实际目标损血；伤害事件触发先后、原生护甲、减免和同步需要游戏验证，不以编辑器静态读取替代。当前本专题尚未做这一整套运行测试。

## 致命一击表现：伤害判断与视觉模块分工

【中心系统 → jianshang_Guai（怪物受伤）→ 判断伤害大于生命后 → 最后一击】在该受伤分支内，比较局部“最终伤害”是否大于或等于目标当时生命；符合时先销毁若干绑定特效。其“最后一击”子分组进一步限制来源是本图模拟英雄伤害的 e002、玩家的“分裂单位2”或“弹射单位”，再显式传玩家和怪物给【中心系统 → zuihouyiji（普攻最后一击）】。这是一条受限定伤害来源和外层事件条件约束的表现链，不能直接等同所有敌人的死亡事件，也不能根据触发器标题认定仅有英雄本体伤害能触发。

被调用模块按玩家查绑定英雄，计算英雄和目标的方向，并为 BOSS/非 BOSS 配置不同的随机移动周期。在0.01秒周期中，尝试沿方向计算新的目标坐标，先检查地形可行走后设置单位 X/Y；结束分支创建朝向相关的流血和血炸特效并销毁特效句柄，再清理计时器。模型表现是否有完整动画应按模型和实际游戏观感核验；销毁特效句柄不应一概解释为画面瞬间消失。目标死亡、移除、位置碰撞及源事件和最终生命变化的先后顺序仍待隔离游戏验证；数值和模型路径为此图样本。`b1（多重射魔兽原生）` 的转换文本还存在同名候选调用，但该调用在当前只读 GUI 中不属于已启用路径，不能算作另一条已经生效的入口。

制作同类技能时应将致命判断、奖励/死亡结算和最后一击视觉作为不同责任；先核对真正生效的事件与马甲来源，再显式传玩家、目标和方向等上下文。若需要死亡后移动尸体、空目标处理或跨越障碍，应按新需求和实际引擎行为验证；不要为每位玩家复制同构触发器，也不要把此图限定来源、时长和资源 ID 自动套用其他地图。
