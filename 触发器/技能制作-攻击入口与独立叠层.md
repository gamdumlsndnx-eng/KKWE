# 技能制作：攻击入口与独立叠层

用于设计普攻触发、临时增益、叠层上限和到期回退。以下是对《一剑爆开天门》启用 GUI 的只读追踪及作者确认，不代表在新地图实现或通过游戏、多人测试；数字和技能键是源码案例，不自动带入其他地图。

## 入口先核对事件，而不是只看文字

【中心系统 → gongji1_Hero】注册 `PlayerUnitEventAttacked`，并筛选攻击者为英雄。其中 FQHC25 和 FQHC40 位于这个攻击事件触发器中；事件本身不能证明攻击最终命中或造成正数伤害。用户此前要求的“实际造成伤害之后触发”必须选择并实测目标地图的伤害事件、实际伤害和来源判断，不能仅依赖攻击事件名称。不同技能可以有不同入口，攻击开始类技能无需统一改成伤害类。

尤其 FQHC25 的分组文字写“攻击命中”，本次看到的所属公共入口是被攻击事件；仅凭静态读取不能认定失手、闪避、伤害被归零时是否仍触发，需按目标版本实际测试，不能以注释替代证据。

## 有上限、每层单独计时

【中心系统 → gongji1_Hero → FQHC25】读取该玩家对应技能的拥有状态，层数小于10时才新增一层，调用属性模块加入力量、敏捷和智力，并为本层启动5秒计时器；到期使层数减一，将该层当初增加的三个具体数值传给属性模块扣回并清理计时器。达到10层时当前分支不新增或刷新原层。作者已确认每层分别计时，且新层应按实时基础属性计算，排除这个技能已有增益；源码已读公式直接读取当前玩家属性，是否排除旧层存在设计差异，不能原样当作已符合意图。

制作类似技能时：记录每个实例的实际增量快照，到期只扣除属于这一层的数值；基础值改变时，后续层按新基础值计算，已经添加的层如何变化按需求决定。不同玩家、英雄替换、死亡、重置或驱散时要定义归属和清理，避免新英雄被旧层的计时器误扣。全属性增益应走目标图真实属性接口，不随意直改与属性系统不一致的字段。

## 无上限、固定值独立回退

【中心系统 → gongji1_Hero → FQHC40】确认技能状态后给绑定英雄的攻击速度加 0.05，并启动3秒计时器，计时器到期减去 0.05 后清理自身；这一分组没有层数上限判断。可将它理解为多次触发各有一个独立计时的固定增量：每次叠加与到期分开，而不是每次触发刷新唯一的3秒。至于引擎对攻速字段的上下限、其他模块并发改写和英雄替换时的最终效果，仍需目标地图验证。

FQHC25 和 FQHC40 都是“增加后延迟扣回”，但一个按本次基础属性生成三个增量、有10层限制；另一个为固定攻速增量、分组内无上限。因此可共用实例生命周期的设计，数值来源、上限、属性接口与对象归属仍须分别配置。

## 持续标记与临时层不是一回事

【中心系统 → gongji1_Hero → BMJSSR+1】破绽标记：作者确认它属于 SSR1 传奇召唤剑，仅作用于 BOSS，BOSS 被标记后所有玩家都享受对该 BOSS 10% 受伤加深。当前分组文字也称 SSR1，但启用动作构造的拥有状态键却是 `BMJSSR+10`，并对攻击目标保存 `BMJSSR1` 和头顶特效；已读入口只筛选攻击者为英雄，在该分组未见明确 BOSS 类型筛选。对隔离转换的 GUI 全文搜索 `BMJSSR1`，目前只看到此处分组的读取/写入；在实时查看的公共伤害、怪物受伤与死亡等主要触发中尚未找到 10% 消费动作。不能排除其他脚本、不同状态键或转换遗漏，也未在游戏复现，不能把设计意图当作已生效结果。

作者确认这份破绽标记**持续到 BOSS 死亡**。新图制作类似共享受伤加深时，应先按目标图的分类识别 BOSS，在该目标上保存状态，再从实际受伤入口或计算器按约定顺序对所有符合的攻击者应用一次 10% 受伤加深；与玩家个人 BOSS 增伤、其他受伤加深和暴击分别约定叠加方式。重复施加如何处理需按技能规则确认；目标死亡时要清理状态及特效，避免错误给小怪或其他 BOSS 加成。只根据攻击开始事件设标记不代表攻击最终造成了伤害，应按新需求选择事件。

其他技能如作者确认的“胆战心惊”由先施加者持有归属，不能当成独立叠层；共享标记、各玩家分别标记、刷新和覆盖应按具体设计区分。

### 单标记、先施加者归属：两种消费入口

【中心系统 → shanghai3 → BMJSSR+8】的施加分支检查怪物 `BMJSSR8=0`，再将标记设为1并把头顶特效保存在该怪的 `绑定特效3`；作者确认每只怪只保留一份，归先施加者。一次技能中的目标枚举与首次攻击目标替换必须逐个核对，不能仅看目标数量认为已经存了施加者。

在【中心系统 → gongji1_guai】的非英雄单位攻击事件中，攻击者为局部“怪物”，玩家取被攻击单位的所属者；胆战心惊分组读取攻击者标记，满足其其他条件时，将标记置零并销毁记录的头顶特效，以当前局部玩家属性和马甲计算后续伤害。另一条【shanghai3 → BMJSSR+8】有冷却分支，枚举带标记的敌人，清除标记和头顶特效后计算及造成伤害。两个入口都会消费标记，不应只在其中一个入口处理归属和清理。

作者明确：玩家甲先施加、怪物后来攻击玩家乙时，应按甲的属性结算，乙不能覆盖甲。当前已读的施加分支只看到保存状态和特效，未见同一处存储施加玩家；攻击入口取的是受攻击单位所属玩家，因此多人跨玩家路径存在与预期不一致的风险，但不能排除其他存储方式或断言游戏已复现。制作同类技能应将施加玩家与状态、特效绑定到目标，消费前读取该归属；不同消费入口应复用同一套状态消费/归属规则，按需求决定何时清除，避免重入时同一标记结算两次。目标死亡清理、施加者退出、英雄替换及多人同时触发仍需测试。

## 检查清单

- 确认事件是攻击开始、实际正数伤害、受伤或死亡，以及英雄、伤害马甲、召唤物的身份和归属。
- 定义上限、每层/全体计时、满层刷新或跳过、数值实时还是快照、对象换人或死亡与驱散后的处理。
- 用逆天局部变量显式传参给既有属性模块；持久层数、每层增量与计时器实例分别归属，避免一组全局变量被多人覆盖。
- 验证同一玩家连续快速触发、多人同时触发、到期交错、装备变化、满层、被驱散和结束路径；GUI读回、保存编译与游戏行为分开记录。
