# 技能制作规范：模块化 GUI、属性与伤害

用途：后续设计或修改 KKWE 技能触发时的工作规则。用户要求：需求未写细时，默认以其《一剑爆开天门-带物编》源码中**对应系统**的成熟模板与逻辑为标准；用户提出具体差异时，以源码逻辑为基础实现差异。应按当前目标地图与需求适配，不假设旧图专属 ID 或依赖一定存在；关键玩法、数值或兼容条件无法合理确定时，先查证并询问用户。该规范目前来自用户说明、指定 KKWE 的函数描述和参考源码的静态分析；逆天传参分组、多次嵌套与多人并发等仍需在可恢复测试地图验证。

## 先确定接口，再写技能

技能只是投射物数量或方向不同时，优先查[多方向投射物模块](技能制作-多方向投射物模块.md)并复用已有同语义实现；命中、追踪、阶段或清理不同时仍需分别设计。

制作按力量等属性百分比结算的技能时，先查[中心伤害计算与力量倍率示例](技能制作-中心伤害计算与力量示例.md)，核对参考图的模式、参数、增伤顺序、技暴、目标结算及作者确认的双重被动增伤；目标图必须重新核实接口，不能将参考图的特殊公式直接泛化。

技能物编默认按作者的模拟技能习惯选择承载；有关月刃模板、按钮 XY、物编到 GUI 的例子和伤害马甲，先看[物编：技能承载与按钮位置](../物编/技能承载与按钮位置.md)。主动操作另按需求选择，不能把被动标识直接当作主动选目标。

多目标是否允许重复、落点重叠伤害、冰冻后其他伤害击杀及阵法死亡后续存，参考[多目标选取、冰冻冰爆与持续法阵](技能制作-多目标选取与冰冻法阵.md)。启用 GUI 已经明确的限制先自行理解，只有实际冲突或规则缺失时再询问作者。

询问用户某个技能的用意或参数时，必须同时写明编辑器中的分类、触发器名称，以及技能或动作分组，例如“中心系统 → gongji1_Hero → FQHC25”；区分代码里看到的事实、自己的推断和需要用户确认的内容，方便用户直接定位。

攻击叠层、目标持续状态、召唤物与 BOSS 多阶段技能的具体设计，参考[叠层、状态、召唤与阶段技能](技能机制-叠层状态召唤与BOSS.md)，并先核对目标地图的属性和模块。

区分可复用的逻辑与参考图专属玩法：作者的《一剑爆开天门》中装备不能丢弃，通过替换或吞噬入体处理，青干被替换后重新计时；其他地图若允许丢弃计时物品，按作者建议以是否携带控制计数，未携带时暂停、重新携带后继续保留的剩余时间，并按目标地图确认转移归属与例外。

先查看[技能分布与学习覆盖](技能分布与学习覆盖.md)：技能效果可能分散在英雄或怪物的攻击、受伤、死亡、周期、召唤和 BOSS 等入口。遇到状态标记应追踪写入、读取、消费和清理，确认施加者与受影响对象的归属，不能只读名称所在的触发器。

需要处理受伤、连锁伤害、暴击回调或多人同时释放时，先看[伤害事件与多人技能规范](伤害事件与多人技能-制作及验证规范.md)，核对各入口条件、嵌套调用、暴击标记与计时器的数据归属。

1. 明确技能玩法：触发事件（施法效果、攻击、受伤、击杀等）、目标、范围、伤害/控制、持续时间、冷却、多人规则、成功与失败条件。需要的游戏规则不清楚时，先分析上下文，仍无法判断时询问用户。
2. 只读核对当前地图：是否有既有公共伤害/属性模块、对象自定义值键、伤害系统、玩家绑定英雄、伤害马甲、技能类型、资源及其初始化。模块不存在、版本不兼容或接口未核实，不直接搬旧地图的触发器名、rawcode、`gg_trg`、全局变量或数值；按新地图重新设计可复用接口，并告知差异。
3. 默认使用可编辑 T/GUI；在语义相同且覆盖正确时优先使用“任意单位/玩家”统一事件，从事件响应取得触发单位与所属玩家，避免复制玩家 1、2、3 的同构触发。不同矩形、事件类型或特殊玩家规则必须分别处理时保留必要差异。
4. 把事件入口与公共效果拆开：入口负责识别事件、筛选技能/目标、获得玩家；公共模块负责计算、效果、提示或属性更新。单次执行的临时数据用逆天局部变量；跨执行持久数据优先沿用目标地图已有的玩家/单位自定义属性；公共配置表与确有必要的全局变量按用途保留。
5. 运行逆天触发时确认目标、是否检查条件、参数名与类型、子动作分组以及回调读写的状态。只传实际需要的上下文；不要假定被调用模块能自动读取所有调用方局部变量。局部数组不能直接穿透逆天计时器或逆天触发器，逆天计时器和逆天注册触发器内不能等待。

用户解释过参考图将本命剑按 R/SR、SSR、UR 分成不同触发，并与法宝等效果分开的用意：它们都是英雄伤害后的技能补充结算，拆分是为了避免单个触发器过长，方便按内容和等级定位、扩展与排错。其他地图可对应装备、宝物等系统；按规模与职责组织，勿因为看到了等级分组就把功能硬拆成无意义的触发器。

## 基础 GUI 结构（按需求填充）

下面是设计骨架，不是可直接粘贴的代码；先使用当前编辑器注册的真实函数与参数类型实现。

```text
触发器：技能入口
事件：任意单位发生所需事件（例如开始生效），以当前需求选择
条件：技能类型/单位/玩家/目标满足规则
动作：
  [逆天] 设置局部「施法单位」= 事件单位
  [逆天] 设置局部「玩家」= 施法单位所属玩家
  [逆天] 设置局部「目标／坐标」= 与本技能相符的事件响应
  [逆天] 运行「技能效果模块」：明确传入玩家、目标及实际所需参数

触发器：技能效果模块（如由入口运行，可无独立事件）
  接收显式传入的局部参数，按玩家或单位读取当前地图已有属性
  选择并运行当前地图的伤害计算模块，取得该模块规定的结果
  根据需求播放效果、执行控制与伤害，并处理计时器、单位组和临时单位
  属性变化通过已核实的属性模块进行；持续状态保存在约定的对象与键上
```

不同技能可能由伤害事件或计时器而非施法事件进入；事件单位、伤害来源、目标单位的含义不可互换。若只有一个入口且无复用需求，也可以合并简单动作，不为了模块化而人为拆成过多触发。

## 参考系统的模块契约：必须先匹配当前地图

以下数值和名称是《一剑爆开天门-带物编》转换结果中的契约示例，不是所有地图的通用规范；仅当目标地图确实包含相同实现时使用。`Dislpay_Sh` 这个拼写也需以实际地图中的触发为准。

| 模块 | 用途与输入 | 输出或约束 |
| --- | --- | --- |
| `Display_ShuXing` 属性加减 | `玩家`、模式 `s` 和需要改变的属性值；已查看的 `s=1` 增加，`s=2` 减少正值分支 | 写回对应玩家自定义属性；零、负数、额外副作用应按实际分支核对 |
| `Display_SXTEXT0` 物品属性 | 依用途指定 `调用类型`、`s`、玩家、物品类型等 | 描述中 `调用类型=属性` 走属性处理，`调用类型=文本` 生成文本；两种情形 `s` 的含义不同 |
| `Dislpay_Sh` 伤害计算 | `玩家`、计算模式 `s`、`伤害参数`，以及实际技能需要的伤害类型等 | 对应参考图从玩家属性读取数据并输出到 `ShangHai[玩家ID]`；同一玩家嵌套调用和输出覆盖尚未验证 |

| 基数 | 物理 `s` | 法术 `s` |
| --- | ---: | ---: |
| 攻击力 | 1 | 11 |
| 三围合计 | 2 | 12 |
| 力量 | 3 | 13 |
| 敏捷 | 4 | 14 |

## 伤害、属性与资源的落实原则

- 伤害入口和伤害来源要一起设计：用户说明让英雄原始伤害归零、由不同马甲给伤害，是为了配合属性系统、简单防作弊，并降低英雄伤害反复进入伤害触发器造成死循环的风险。参考图按玩家绑定不同马甲：分裂单位3用于模拟英雄伤害，分裂单位2用于区分多重箭，分裂单位参与部分技能的实际伤害；它们不能因名字相近就合并。实现时逐条核对伤害事件的来源、伤害类型、筛选、再次给伤害后的入口与递归防护；使用马甲本身不保证所有分支都不会循环。[本命剑数据与伤害流程](本命剑技能-数据驱动与伤害流程.md)给出可复用案例。
- 分清玩家、英雄本体、技能目标、马甲及物品类型分别作为哪类对象。用户解释过参考图的“分裂单位2”用于区分多重箭和英雄主攻击，并与属性系统、防作弊设计配合；在沿用相同系统时维持该区分，不随意把所有伤害改由英雄本体发出。新地图必须核对实际伤害归属规则，不能无条件照搬这个单位。
- 技能暴击、普通暴击、技暴伤害等是绑定属性系统的独立属性；技能既可能读取属性，也可能运行公共模块修改属性。按当前系统核对基础属性与结果属性、数据键、伤害类型、加减方式和更新时机。
- 识别由技能伤害再次触发受伤事件、技暴附加技能、反伤、击杀等可能形成的嵌套路径；按实际玩法使用独立来源标记或冷却状态，避免误触和递归，但不要未经验证声称某个标记能防止所有递归或作弊。
- 同一只 BOSS 的技能可以共享最低释放间隔，避免多个技能重叠；用户同时确认“天门落剑”是例外，主要由魔法值限制自身，释放后再限制其他技能。新 BOSS 按用户玩法重新设定，不把单个旧技能的例外或参数泛化。
- 与地图现有触发一致地管理临时点、组、特效、计时器和马甲的创建、使用与清理；临时组仅在最后一次使用后销毁。检查延时后目标死亡或离开、不同玩家交错触发及冷却恢复。只凭静态源码不能证明计时器和局部变量的并发安全。

## 主动技能、物品和持久开关

主动技能的物编承载需要与 GUI 的事件及目标一致：参考图【宝宝技能 → BB_W / BB_E】分别在任意单位施放技能事件筛选 A050/A051，读取施法者、所属玩家和目标点，再判断目标点是否位于其他在线玩家关闭的练功房；允许后分别枚举区域内物品拾取，或遍历物品栏将物品放到目标点。拾取分支排除隐藏、生命不大于0和类型标记为灾厄宝箱的物品；这属于本图规则，不应擅自套用其他地图。A050/A051 的物编基于通魔，分别配置 W/E 热键与目标技能；被动标识和带目标的主动技能必须按用途分别选模板。目标点、临时矩形结束后各自移除；物品栏已满、无物品、路径阻挡、交互重入与联机同步仍需游戏验证。

可切换状态的主动技能要串联“显示、实际权限、跨局恢复”：参考图【宝宝技能 → BB_3_1 / BB_3_2】使用技能生效事件，互换 A092/A093 按钮，并在玩家对象上写入“岛屿关闭”；【宝宝技能 → bb_get1～4】和 BB_W/BB_E 等再读取该状态检查其他玩家的进入或物品操作；【英雄系统 → hero_Set → 宝宝练功房开关】依据玩家存档的第三位恢复状态与按钮。作者确认重新进图应保留上次的开放或关闭选择。当前两条启用保存分支均把第三位设为1，初始化读取1恢复关闭，与作者意图存在静态差异，尚需存档加载和游戏复核，不直接修改源码。制作新图时应明确定义各编码值及默认值，检查互换技能、即时权限、保存、读取与恢复是否一一对应，并保留存档中其他位；不得照搬参考图专属存档键或平台 API。

## 写完后的检查

确认事件、条件、目标、模块和参数结构与需求相符；从 KKWE 读回 GUI，核对启用状态、嵌套分组、属性和对象引用。该版本 MCP 的 `validate_triggers` 曾导致崩溃，不调用它。编译、手动保存、重新打开与实际游戏结果分别验证并如实报告；不以静态阅读或接口返回成功替代这些验证。知识库按问题读取，遇到未确认的参数或目标地图缺少依赖时明确标注并先查证。

## 技能获得、套装吞噬与更换英雄

参考图【UI【法宝】 → UI1AA（直接获得法宝）】为玩家和法器构造 FQA 状态键，设置“已拥有”，同时增加对应套装数量并调用单件属性模块；【FQ_HeCheng（宝物吞噬合成）】则构造 FQHC 键，设置“已吞噬”，并调用套装属性模块。两个状态不是同义词：某些技能在持有时运行，另一些只在吞噬后运行。单件属性加减包装分别向物品属性模块传入同一玩家与物品类型，并使用 s=1 或 s=2；这些调用方式只适用于已核实相同接口的地图。

【英雄系统 → hero_display2（换英雄继承属性）】记录旧英雄 Q/W/E/R 剩余冷却、拆存物品，创建新英雄并把玩家的“绑定英雄”改为新单位；随后恢复部分单位状态、物品及已有技能。作者确认更换英雄或皮肤时，各技能应各自保留剩余冷却，不因 Q/W/E/R 位置相同把旧技能冷却直接转给不同的新技能。作者补充该功能与英雄、吞噬装备和吞噬技能等多个模块联动；此次只在该触发器看到读取 CD1～CD4，不能排除其他模块，也不能据此认定故障。需沿技能身份、吞噬/装备和英雄更换的完整链路追踪实际写入与恢复，并核对目标图及本次需求。玩家状态可以继续绑定玩家，但旧英雄上的临时效果与计时器必须分别定义归属；不能把旧单位残留的层或清理回调误作用于新英雄。

新技能制作时同时核对：如何获得、是否需要吞噬、属性增加与移除、技能承载、玩家与英雄绑定、换英雄和复活后的状态继承。它们是技能生命周期的一部分，不应只检查释放触发器；GUI 静态结果与多人游戏验证分别记录。

具体状态需要同时核对“键”和“字段”，不能只看 FQA/FQHC 前缀：【ui_DisplayGet_ShuXingTUN → FQA156】本身也区分 FQA156 的“已拥有”与“已吞噬”，后者参与特殊合成判断；FQHC 则有套装吞噬状态。另在【UI【本命剑】 → UI1d】里，技能槽的 BMJJN“已拥有技能”、实际添加的技能及本命剑标识的“已拥有”分别保存，作用不同。新图应明确获得、吞噬、技能槽和物编承载之间的对应关系，并核验替换或移除时各状态和属性的撤销。
