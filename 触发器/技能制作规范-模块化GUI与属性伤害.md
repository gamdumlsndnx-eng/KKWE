# 技能制作规范：模块化 GUI、属性与伤害

用途：后续设计或修改 KKWE 技能触发时的工作规则。用户要求：需求未写细时，默认以其《一剑爆开天门-带物编》源码中**对应系统**的成熟模板与逻辑为标准；用户提出具体差异时，以源码逻辑为基础实现差异。应按当前目标地图与需求适配，不假设旧图专属 ID 或依赖一定存在；关键玩法、数值或兼容条件无法合理确定时，先查证并询问用户。该规范目前来自用户说明、指定 KKWE 的函数描述和参考源码的静态分析；逆天传参分组、多次嵌套与多人并发等仍需在可恢复测试地图验证。

## 先确定接口，再写技能

技能只是投射物数量或方向不同时，优先查[多方向投射物模块](技能制作-多方向投射物模块.md)并复用已有同语义实现；命中、追踪、阶段或清理不同时仍需分别设计。

制作按力量等属性百分比结算的技能时，先查[中心伤害计算与力量倍率示例](技能制作-中心伤害计算与力量示例.md)，核对参考图的模式、参数、增伤顺序、技暴、目标结算及作者确认的双重被动增伤；目标图必须重新核实接口，不能将参考图的特殊公式直接泛化。

技能物编默认按作者的模拟技能习惯选择承载；有关月刃模板、按钮 XY、物编到 GUI 的例子和伤害马甲，先看[物编：技能承载与按钮位置](../物编/技能承载与按钮位置.md)。主动操作另按需求选择，不能把被动标识直接当作主动选目标。

多目标是否允许重复、落点重叠伤害、冰冻后其他伤害击杀及阵法死亡后续存，参考[多目标选取、冰冻冰爆与持续法阵](技能制作-多目标选取与冰冻法阵.md)。启用 GUI 已经明确的限制先自行理解，只有实际冲突或规则缺失时再询问作者。

询问用户某个技能的用意或参数时，必须同时写明编辑器中的分类、触发器名称，以及技能或动作分组，例如“中心系统 → gongji1_Hero → FQHC25”；区分代码里看到的事实、自己的推断和需要用户确认的内容，方便用户直接定位。

攻击叠层、目标持续状态、召唤物与 BOSS 多阶段技能的具体设计，参考[叠层、状态、召唤与阶段技能](技能机制-叠层状态召唤与BOSS.md)，并先核对目标地图的属性和模块。

区分可复用的逻辑与参考图专属玩法：作者的《一剑爆开天门》中装备不能丢弃，通过替换或吞噬入体处理，青干被替换后重新计时；其他地图若允许丢弃计时物品，按作者建议以是否携带控制计数，未携带时暂停、重新携带后继续保留的剩余时间，并按目标地图确认转移归属与例外。

先查看[技能分布与学习覆盖](技能分布与学习覆盖.md)：技能效果可能分散在英雄或怪物的攻击、受伤、死亡、周期、召唤和 BOSS 等入口。遇到状态标记应追踪写入、读取、消费和清理，确认施加者与受影响对象的归属，不能只读名称所在的触发器。

需要处理受伤、连锁伤害、暴击回调或多人同时释放时，先看[伤害事件与多人技能规范](伤害事件与多人技能-制作及验证规范.md)，核对各入口条件、嵌套调用、暴击标记与计时器的数据归属。

1. 明确技能玩法：触发事件（施法效果、攻击、受伤、击杀等）、目标、范围、伤害/控制、持续时间、冷却、多人规则、成功与失败条件。需要的游戏规则不清楚时，先分析上下文，仍无法判断时询问用户。
2. 只读核对当前地图：是否有既有公共伤害/属性模块、对象自定义值键、伤害系统、玩家绑定英雄、伤害马甲、技能类型、资源及其初始化。模块不存在、版本不兼容或接口未核实，不直接搬旧地图的触发器名、rawcode、`gg_trg`、全局变量或数值；按新地图重新设计可复用接口，并告知差异。
3. 默认使用可编辑 T/GUI；在语义相同且覆盖正确时优先使用“任意单位/玩家”统一事件，从事件响应取得触发单位与所属玩家，避免复制玩家 1、2、3 的同构触发。不同矩形、事件类型或特殊玩家规则必须分别处理时保留必要差异。
4. 把事件入口与公共效果按职责拆开。参考作者惯例，高频公共计算结果和配置优先评估触发器全局变量/按玩家索引的数组；单次上下文用逆天局部变量，对象绑定、持久状态可使用逆天自定义值。必须结合目标地图已有体系选择，不把任何一种方式当成唯一方案。按玩家索引不解决同一玩家的嵌套覆盖；后续嵌套或延时使用前保留该次结果和暴击等状态。
5. 跨触发器运行时核对目标、条件、参数和分组，只传必要上下文。同一触发器的逆天计时器优先参照作者现有写法，不机械地为每个局部变量重复添加传参；需要固定当次数值、隔离并发或跨触发器使用时显式快照/传递。局部数组的跨界、嵌套调用和回调继承按当前版本核对并测试；逆天计时器和逆天注册触发器内不能等待。

## 命名、顺序、特效与可见性

- 用户希望按实际事件简洁命名：`英雄受伤`、`英雄伤害`、`英雄攻击`、`怪物受伤`、`怪物被攻击`。名字必须对应真实事件语义；技能专属子触发可写成“技能名-具体作用”，方便定位。按 `N-M   【名称】` 及数字后三空格，分类内从小到大；公共核心在上、技能在下。插件插入位置需读回验证，若缺少可靠排序接口，不得把倒序称作已完成。复杂关键分支写少量说明用途或特殊规则的注释。
- 用户指出先前测试图把高频伤害结果写入玩家逆天自定义值不符合其偏好。参考源码【一些触发传输 → Dislpay_Sh】把结果写入全局数组 `ShangHai[id]`，`ShangHai_BaoJi[id]` 记录技暴；这支持按玩家索引的高频共享方案，但同玩家重入可能覆盖，不能仅凭数组断言完全安全。
- 用户希望一开始就为特效保留玩家开关。参考【中心系统 → shanghai2 → BMJR+1 玄铁剑】按单位类型 `YDWEGetObjectPropertyString(..., "file")` 读取模型路径；`GetLocalPlayer` 对应的“特效显示”为0时切换本地视觉模型字符串，再在同一同步流程创建和操作视觉马甲。【UI【控制台】→ tbKong（同步控制台按钮2）】有同步事件接收玩家操作并更新该玩家开关。这里只是源码静态证据，具体目标版本的本地模型 API、空路径占位与多人安全需实测；单位创建/删除、伤害、计时、随机数等游戏状态保持同步。按用户需求默认预留接口，但已有地图优先使用其开关，不复制参考图固定键、模型或路径。
- 伤害和普攻马甲与特效马甲分工。参考图 `e000/e002` 的物编记录空模型、零碰撞、隐藏小地图，配合蝗虫/无敌及玩家绑定；具体原图 GUI 绑定可见于【地图初始化 → DayOff2】。这些仅是本图证据。新图应检查实际默认模型、编辑器/小地图与游戏内可见性、对象归属、碰撞、生命周期和攻击能力；只设置某个实例透明不能假定所有马甲都已不可见。攻击残影使用非英雄特效马甲，避免干扰英雄死亡与其他事件。

用户解释过参考图将本命剑按 R/SR、SSR、UR 分成不同触发，并与法宝等效果分开的用意：它们都是英雄伤害后的技能补充结算，拆分是为了避免单个触发器过长，方便按内容和等级定位、扩展与排错。其他地图可对应装备、宝物等系统；按规模与职责组织，勿因为看到了等级分组就把功能硬拆成无意义的触发器。

## 基础 GUI 结构（按需求填充）

下面是设计骨架，不是可直接粘贴的代码；先使用当前编辑器注册的真实函数与参数类型实现。

```text
触发器：技能入口
事件：任意单位发生所需事件（例如开始生效），以当前需求选择
条件：技能类型/单位/玩家/目标满足规则
动作：
  [逆天] 设置局部「施法单位」= 事件单位
  [逆天] 设置局部「玩家」= 施法单位所属玩家
  [逆天] 设置局部「目标／坐标」= 与本技能相符的事件响应
  [逆天] 运行「技能效果模块」：明确传入玩家、目标及实际所需参数

触发器：技能效果模块（如由入口运行，可无独立事件）
  接收显式传入的局部参数，按玩家或单位读取当前地图已有属性
  选择并运行当前地图的伤害计算模块，取得该模块规定的结果
  根据需求播放效果、执行控制与伤害，并处理计时器、单位组和临时单位
  属性变化通过已核实的属性模块进行；持续状态保存在约定的对象与键上
```

不同技能可能由伤害事件或计时器而非施法事件进入；事件单位、伤害来源、目标单位的含义不可互换。若只有一个入口且无复用需求，也可以合并简单动作，不为了模块化而人为拆成过多触发。

## 伤害、属性与资源的落实原则

- 伤害入口和伤害来源要一起设计：用户说明让英雄原始伤害归零、由不同马甲给伤害，是为了配合属性系统、简单防作弊，并降低英雄伤害反复进入伤害触发器造成死循环的风险。参考图按玩家绑定不同马甲：分裂单位3用于模拟英雄伤害，分裂单位2用于区分多重箭，分裂单位参与部分技能的实际伤害；它们不能因名字相近就合并。实现时逐条核对伤害事件的来源、伤害类型、筛选、再次给伤害后的入口与递归防护；使用马甲本身不保证所有分支都不会循环。[本命剑数据与伤害流程](本命剑技能-数据驱动与伤害流程.md)给出可复用案例。
- 分清玩家、英雄本体、技能目标、马甲及物品类型分别作为哪类对象。用户解释过参考图的“分裂单位2”用于区分多重箭和英雄主攻击，并与属性系统、防作弊设计配合；在沿用相同系统时维持该区分，不随意把所有伤害改由英雄本体发出。新地图必须核对实际伤害归属规则，不能无条件照搬这个单位。
- 技能暴击、普通暴击、技暴伤害等是绑定属性系统的独立属性；技能既可能读取属性，也可能运行公共模块修改属性。按当前系统核对基础属性与结果属性、数据键、伤害类型、加减方式和更新时机。
- 识别由技能伤害再次触发受伤事件、技暴附加技能、反伤、击杀等可能形成的嵌套路径；按实际玩法使用独立来源标记或冷却状态，避免误触和递归，但不要未经验证声称某个标记能防止所有递归或作弊。
- 同一只 BOSS 的技能可以共享最低释放间隔，避免多个技能重叠；用户同时确认“天门落剑”是例外，主要由魔法值限制自身，释放后再限制其他技能。新 BOSS 按用户玩法重新设定，不把单个旧技能的例外或参数泛化。
- 与地图现有触发一致地管理临时点、组、特效、计时器和马甲的创建、使用与清理；临时组仅在最后一次使用后销毁。检查延时后目标死亡或离开、不同玩家交错触发及冷却恢复。只凭静态源码不能证明计时器和局部变量的并发安全。

## 主动技能、物品和持久开关

主动技能的物编承载需要与 GUI 的事件及目标一致：参考图【宝宝技能 → BB_W / BB_E】分别在任意单位施放技能事件筛选 A050/A051，读取施法者、所属玩家和目标点，再判断目标点是否位于其他在线玩家关闭的练功房；允许后分别枚举区域内物品拾取，或遍历物品栏将物品放到目标点。拾取分支排除隐藏、生命不大于0和类型标记为灾厄宝箱的物品；这属于本图规则，不应擅自套用其他地图。A050/A051 的物编基于通魔，分别配置 W/E 热键与目标技能；被动标识和带目标的主动技能必须按用途分别选模板。目标点、临时矩形结束后各自移除；物品栏已满、无物品、路径阻挡、交互重入与联机同步仍需游戏验证。

可切换状态的主动技能要串联“显示、实际权限、跨局恢复”：参考图【宝宝技能 → BB_3_1 / BB_3_2】使用技能生效事件，互换 A092/A093 按钮，并在玩家对象上写入“岛屿关闭”；【宝宝技能 → bb_get1～4】和 BB_W/BB_E 等再读取该状态检查其他玩家的进入或物品操作；【英雄系统 → hero_Set → 宝宝练功房开关】依据玩家存档的第三位恢复状态与按钮。作者确认重新进图应保留上次的开放或关闭选择。当前两条启用保存分支均把第三位设为1，初始化读取1恢复关闭，与作者意图存在静态差异，尚需存档加载和游戏复核，不直接修改源码。制作新图时应明确定义各编码值及默认值，检查互换技能、即时权限、保存、读取与恢复是否一一对应，并保留存档中其他位；不得照搬参考图专属存档键或平台 API。

## 写完后的检查

确认事件、条件、目标、模块和参数结构与需求相符；从 KKWE 读回 GUI，核对启用状态、嵌套分组、属性和对象引用。该版本 MCP 的 `validate_triggers` 曾导致崩溃，不调用它。编译、手动保存、重新打开与实际游戏结果分别验证并如实报告；不以静态阅读或接口返回成功替代这些验证。知识库按问题读取，遇到未确认的参数或目标地图缺少依赖时明确标注并先查证。

## 技能获得、套装吞噬与更换英雄

参考图【UI【法宝】 → UI1AA（直接获得法宝）】为玩家和法器构造 FQA 状态键，设置“已拥有”，同时增加对应套装数量并调用单件属性模块；【FQ_HeCheng（宝物吞噬合成）】则构造 FQHC 键，设置“已吞噬”，并调用套装属性模块。两个状态不是同义词：某些技能在持有时运行，另一些只在吞噬后运行。单件属性加减包装分别向物品属性模块传入同一玩家与物品类型，并使用 s=1 或 s=2；这些调用方式只适用于已核实相同接口的地图。

【英雄系统 → hero_display2（换英雄继承属性）】记录旧英雄 Q/W/E/R 剩余冷却、拆存物品，创建新英雄并把玩家的“绑定英雄”改为新单位；随后恢复部分单位状态、物品及已有技能。作者确认更换英雄或皮肤时，各技能应各自保留剩余冷却，不因 Q/W/E/R 位置相同把旧技能冷却直接转给不同的新技能。作者补充该功能与英雄、吞噬装备和吞噬技能等多个模块联动；此次只在该触发器看到读取 CD1～CD4，不能排除其他模块，也不能据此认定故障。需沿技能身份、吞噬/装备和英雄更换的完整链路追踪实际写入与恢复，并核对目标图及本次需求。玩家状态可以继续绑定玩家。作者说明本图换英雄会统一继承当前属性，技能侧不需要重复做整套继承；应继承的临时层及其计时器到期时应按各自剩余时间正确对当前英雄或公共属性接口扣回，避免重复扣除或误扣其他玩家。

新技能制作时同时核对：如何获得、是否需要吞噬、属性增加与移除、技能承载、玩家与英雄绑定、换英雄和复活后的状态继承。它们是技能生命周期的一部分，不应只检查释放触发器；GUI 静态结果与多人游戏验证分别记录。

具体状态需要同时核对“键”和“字段”，不能只看 FQA/FQHC 前缀：【ui_DisplayGet_ShuXingTUN → FQA156】本身也区分 FQA156 的“已拥有”与“已吞噬”，后者参与特殊合成判断；FQHC 则有套装吞噬状态。另在【UI【本命剑】 → UI1d】里，技能槽的 BMJJN“已拥有技能”、实际添加的技能及本命剑标识的“已拥有”分别保存，作用不同。新图应明确获得、吞噬、技能槽和物编承载之间的对应关系，并核验替换或移除时各状态和属性的撤销。

### 替换、入体与冷却恢复的进一步检查

- 普通替换入口【UI【法宝】→ UI1b】接收同步玩家与槽位，使用该玩家的“UI替换法器CD中”标记防连点并在约 0.6 秒后清除；对有物品的槽位，移除旧物品并调用单件属性减少模块，再调用获得模块，随后撤销旧法器的“已拥有”并减少对应套装数量。编写同类操作时，应把替换前后的物品、属性、拥有状态、数量、物品池及防连点一起核对；尤其注意新旧法器相同或关联时的调用先后，不能只看 UI 显示。
- 【FQ_HeCheng】从“英雄拾取法器”事件进入，读取物品类型的套装元数据和玩家套装数量；符合当前非特殊套装条件后设置对应 FQHC 的“已吞噬”，移除相关实物，并调用套装属性模块。实际分支还有物品池、表现和例外；不是每一次拾取都必然吞噬，也不应把此套装路径当作所有单件特殊入体的实现。
- 【Dp_RTFB2】是被调用的直接入体相关模块：源码注释说明先等待约 0.3 秒让可能的合成先处理，随后检查物品状态、从英雄身上移除并更新法宝背包图标；在本模块看到的动作中不能单凭它的名称认定已写入所有“已吞噬”标记。新图应明确由哪个调用方负责标记、属性和去重，检查延迟期间物品或英雄发生变化的情况。
- 原生技能剩余冷却与被动效果的自定义计时分开追踪。【hero_display2】已在实时 GUI 及转换文件中读到原英雄 Q/W/E/R 对应技能的冷却并记录局部 CD1～CD4；本触发已读树中尚未找到这些局部值的恢复动作，但外部机制尚未排除。作者确认设计是按技能身份保留剩余冷却；无论按原生技能还是自定义计时实现，换英雄后都应核对相同技能、不同技能、技能重建及多个玩家的表现，不能把“按槽记录”直接等同于“按技能成功恢复”。
- **进一步限定检索范围**：对隔离转换的 GUI 文件检索技能冷却设置和 CD1～CD4，并从当前 KKWE 读回 hero_display2：可见树中有4次读取对应技能冷却，未发现 YDWESetUnitAbilityState。其他已定位设置动作包括剑道、境界、挑战 NPC 和宝宝相关触发，不能仅因含冷却就断定是换英雄恢复。此检索未覆盖全部动态自定义键、加密脚本、插件内部逻辑或游戏运行，不能据此认定功能不存在或地图有 bug。新系统按玩家及具体技能身份处理，同一槽位换成另一技能不能直接继承旧技能冷却；技能暂时移除后时间继续还是暂停，按目标图设计确定。
- 【JianJN_Use】可见另一种用途：施法效果事件后经约 0.03 秒为当前施放技能设置 1 秒原生冷却。这是本图剑道入口的具体处理，不代表所有技能冷却都应延迟 0.03 秒或统一为 1 秒。技能提示中的冷却、原生技能剩余冷却和玩家状态/计时器内置冷却，要确认哪一项控制实际效果并保持一致。

上述为部分实时 GUI 对照与源码静态追踪；未做换英雄、替换、吞噬及多人游戏实测。FQA、FQHC 等键名和数值属于参考图，新图须依据实际系统映射。

## 多方向弹道：方向、命中与共享资源

参考【中心系统 → shanghai（英雄+法宝伤害）→ 英雄伤害 → FQA50 玄箭】的启用 GUI：入口从正伤害事件获取伤害来源、被击目标和玩家，再读取玩家绑定英雄；该英雄伤害分支检查模拟英雄伤害的来源类型。这个入口依赖参考图现有的伤害体系，新图必须重新确认事件、归属和防递归，不能把“单位被攻击”当作“实际造成伤害”。

该分支从英雄位置出发，按英雄指向本次目标的角度生成三道，间隔为20度；循环计算出的方向依次为中心、中心+20度、中心-20度。每条弹道以0.02秒周期沿自己的方向移动，每步30坐标单位，并在移动位置附近枚举敌人；同一轮弹道共用命中单位组，已记录的单位不再重复伤害。伤害通过公共计算模块与相应伤害马甲处理；伤害参数和 FQHC19 增益依赖其他分支，不能直接复制为独立技能默认值。

制作类似技能时，将发射数量、角度间隔、目标方向、每步距离、周期、射程、范围和每个目标的命中规则分别明确；方向数量变化应复用同一套生成逻辑。允许多道各命中一次与整轮最多命中一次，需要分别选择独立或共享记录，不能单凭视觉弹道推断。参考源码由编号为最后一条的弹道回调清理共享单位组，但不同弹道可能因地形等原因在不同时间结束；当前未验证各结束顺序的运行安全性。新的共享资源应在所有使用它的弹道结束后才释放，例如为每轮记录尚存弹道数，并处理地形阻挡、目标失效、施法者死亡和提前终止；每个实例分别清理自己的特效与计时器。动画是否播放及结束方式按模型和技能要求决定：需要死亡动画的特效马甲可播放后再移除；作者说明这类马甲播放完后通常已不可见，后续移除用于减少单位占用并释放资源。移除时间可参考模型死亡动画时长，不清楚时一般可用1秒；具体还应结合物编、动画速度及游戏观感核对。没有死亡动画或不需要结束动画的效果可直接删除。

以上是编辑器 GUI 静态追踪及通用制作建议，不代表参考技能所有边界已经游戏验证；移动步长除以周期仅是理论速度，真实视觉速度和表现需实际测试。

## 随机落点与延迟范围伤害

参考【中心系统 → shanghai → 英雄伤害 → FQA49 玄破】的启用 GUI：先以绑定英雄为中心，在攻击范围内收集符合条件的候选；有候选时，每轮随机选择一个，记录其当时坐标，随后按计时器延迟在记录的位置枚举受击单位并造成范围伤害。选取使用同一个候选数组，已选择的目标没有在该分支中移除；因此多次选取允许重复，重叠落点的伤害也需要按技能需求单独规定。技能将拥有状态和内置冷却归属于玩家与技能，伤害由公共计算及马甲承担。代码中的筛选使用固定玩家阵营，不能当成其他地图通用的敌我判断；延时后对当前位置范围进行筛选，不等同于追踪原选中单位。

用户已确认部分范围技能需要整次释放共享一次技能暴击判定，而每个受击对象分别判断 BOSS 增伤。制作这类技能时，可将本次释放需共享的随机结果和数值快照与落点数据传给后续模块，再在每个实际命中目标上计算目标相关修正；按该技能的要求决定属性是触发时快照还是命中时读取。上例公共伤害计算在选取落点和范围枚举之前已发生，不能假设它已逐目标判断 BOSS；新技能应按明确的目标规则设计和验证。需另核查无目标、重复落点、目标移动或死亡、多人同时触发和计时器提前结束时的行为，静态追踪不等于已完成游戏测试。

## BOSS 多方向预警与落点一致性

参考【存档BOSS → CundangBOSSA9（前方多方向圈炸）】的启用 GUI，读取 BOSS 和目标的位置计算主方向，以三个方向、每个方向五个落点构造预警；约0.8秒后再次按相同坐标算法生成伤害范围。伤害前建立本轮共用的单位组，命中后加入，整轮检查组内记录后才决定是否再次伤害，遍历结束销毁组。该技能的预警、延迟、敌我和排除建筑筛选与 BOSS 内置及共享施法间隔都是互相关联的；同一轮不重复命中是这处源码的写法，其他技能是否可重复命中应按需求设置。

制作类似预警时应保存本轮方向和落点或确保预警与结算使用相同快照，避免目标或 BOSS 移动后出现“警告在这里、伤害在别处”。还须明确 BOSS 死亡后已发出的预警是否继续结算、是否生成后续预警，并检查死亡、提前打断和计时器退出时的资源清理；不能把单个 BOSS 的处理复制成所有技能的统一规则。上述源码行为是静态分析，计时、多人及游戏表现仍需验证。

## 装备词条与技能、属性联动

参考【UI【衣服武器】词条3选1 → UIf1_tb1（同步武器3选1）】：接收同步玩家和选择参数，按玩家与选项查词条物品类型，设置该玩家的防连点状态，再将玩家、类别和物品类型传给【Dp_yifqJL（衣服武器奖励传输）】。已读代码还把界面隐藏、透明度等显示操作限制在相应本地玩家，而属性与状态写入位于同步触发流程；这只说明当前代码结构，不能单凭静态阅读保证所有多人同步安全。

奖励模块对普通词条从物品类型读取多项属性，统一传给属性加减模块；特殊词条则按玩家及词条参数记录“已拥有”，部分立即调用其他模块，部分由英雄死亡、怪物死亡等触发读取后生效。新技能或词条应连同选择 UI、同步入口、实际属性、生效事件、状态所有者及撤销/替换方式一起追踪；不要只更新说明文字或只检查获得时的奖励。

【Dp_yifqJL → 特殊词条参数9】在获得时读取玩家木头，按本图上限计算扣除额和延迟返还额，180秒后再把当时算出的返还额传给属性模块；这是一次触发上下文的快照，不是到期时重新读取现有木头。源码所见该延时回调内未找到显式清理计时器动作；逆天实现是否另有清理及实际资源行为仍待核实，不能仅凭这一处断言已发生泄漏。设计同类延时奖励时应明确本金、上限、取整、玩家退出/失效、重复获取，以及计时器与局部数据的正常和异常清理。
