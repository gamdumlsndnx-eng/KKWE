# 练功房与地图初始化：制作规范和源码证据

用途：根据用户《一剑爆开天门-带物编》的相关系统设计新地图或调整练功房。需求未写细时，以本源码对应功能的逻辑为起点，结合用户新要求和目标地图实际依赖适配。以下内容来自隔离转换结果和用户此前的说明，尚未在源码图逐项读回或进游戏复核；不能把静态观察视为已经完成移植或验证。

## 应先建立的数据和依赖

1. **玩家范围**：参考图 `01-地图初始化/09-DayOff.lml` 在地图初始化时循环玩家 1～4，检查用户控制和游戏中状态，把符合条件的玩家加入 `WJZ`。后续周期模块通过玩家组枚举处理；新地图应以实际玩法设置玩家范围，而不是为每个玩家复制同构触发。
2. **玩家绑定**：`01-地图初始化/10-DayOff2.lml` 的 0 秒一次性初始化给各玩家关联 `敌对玩家`、给敌方玩家保存 `绑定玩家`，并建立 `分裂单位`、`分裂单位2` 等对象关联。参考图还为玩家配置预放置矩形与单位。新地图的玩家、矩形、单位和物编 ID 须根据自身配置建立，不直接搬参考图的 ID。
3. **练功房数据**：`22-【练功房】/01-ALL_Set2__练功房__.lml` 为有效玩家设置初始 `练功房数量1=10`、`刷怪级别=1`、`精英怪木头=35.00` 等，并关联练功房总区域、普通怪/精英区域以及按等级的普通怪、金猪、精英类型表。这些是参考图示例，新的游戏规则或用户要求优先。
4. 玩家数据用逆天对象自定义值按玩家存取；一次执行临时的玩家、怪物类型、区域、坐标和数量优先使用逆天局部变量。真正需要的共享配置表可以保留全局数组，不把所有操作都改成全局变量。
5. **初始化不一定靠地图开始事件自动运行**：`21-【进攻怪】/1-ALL_Set1__进攻怪__.lml` 内的 0 秒事件处于禁用状态，但 `12-UI【难度选择】和Debuff/05-UI_ND_dp__难度设置【★】__.lml:82-145` 在难度设置流程写入 `hard`，并通过一次性计时器调用 `ALL_Set1`。后者配置 `pointerTime=180.00`、启动进攻波计时器并设置怪物类型表；因此不能因为事件禁用就把该触发整个判定为无用。调用顺序、所有初始化条件和真实时序仍需源码 GUI 与游戏验证。

## 事件与模块的分工

- `02-【中心系统/24-Meimiao__每秒中心计时器__.lml` 使用 1 秒周期事件，枚举 `WJZ`，在相关条件下更新每位玩家的 `每秒计数`，再通过逆天运行 `Meimiao1` 并传该玩家。不同模块是否需要在每秒循环中运行，应以实际玩法和效率为准。
- `02-【中心系统/25-Meimiao1__练功房__.lml` 自身无事件，接收玩家并读取玩家数据。转换结果中，在 `hard>0`、最终 BOSS 未击杀且玩家 `每秒计数` 整除 30 时，若 `练功房数量1<25`，则增加该玩家的基础数量 1，并以当前等级的普通怪类型调用“单个刷怪”；接着统计总区域中类型数据标记 `是精英怪=1` 的单位，数量小于 6 时调用“单个刷怪”并传 `s=2`。用户确认：这个设计是让普通怪基础数量逐步增长，并限制场上精英数量。具体计时、每次触发数量、存活判断及游戏效果仍须在源码编辑器和游戏中核验。
- `22-【练功房】/09-in_LGF.lml` 对多个不同矩形注册进入事件，筛选存活英雄，取得所属玩家后调用公共“全部刷怪”。四个不同区域事件不等于四套玩家触发；能否进一步合并要由地图区域设计决定。
- `05-Display_chuguai1__练功房刷怪单个__.txt` 的原触发器描述列出 `s=0` 为普通怪、`s=2` 为精英；具体 GUI 的普通与精英分支还有不同区域、物编、模式条件和创建后传输。`Meimiao1` 普通怪调用片段仅明确传 `玩家` 和 `nn`，不能在核实前假定未显式传入的 `s` 一定继承或为零。
- `04-shuagua_wp.lml` 使用任意单位施法效果并通过技能对象属性筛选刷怪技能；枚举并筛选旧怪后向公共单刷模块传玩家与 `nn`。多个入口可以复用模块，但传参、单位组和关联数据清理均须逐项核对。
- `07-Display_chuguai4__B计划刷怪__.lml` 读取区域中的普通怪数量，并比较目标数量；转换中可见 `num1 = min(15 - 当前数量 + 4, 目标数量 - 当前数量)`（当前数量低于 15 的分支）。用户确认设计意图是先补到 15，再额外加 4，例如当前 14 只、目标缺口足够时增加 5 只；转换中还会限制不超过目标缺口。用户说明 A 计划是一般使用的刷怪方案，B 计划是防止极端情况下 A 计划失效的备用方案。B 计划的实际调用方、启用条件和运行时行为仍需核对；不把 B 计划当作日常主刷怪机制，也不把参考图数字无条件套到新地图。
- 进攻怪是另一条独立链：`21-【进攻怪】/3-ChuGuai__进攻__.lml` 监听 `JSQ_Start` 到期，推进 `point` 波数并调用进攻怪创建模块；可见在部分波次通过计时调用 BOSS 模式。`4-Display_chuguai4__进攻出怪__.lml` 在两个区域创建单位并向基地发布巡逻命令。其普通怪部分转换输出的条件为空，不能未经编辑器核实就声称 `s=2` 时只会执行 BOSS 分支；波次、计时和游戏效果尚待验证。

## 英雄等级与属性初始化的关联

- `23-【英雄】系统+等级系统/18-Lv_Set.lml` 在 0 秒事件中循环有效玩家，按玩家保存初始 `等级=1`，并按整数等级键保存 `需求经验`；部分等级区间由 3 秒、4 秒的一次性计时器分批建立。经验表的完整范围、分批目的及游戏运行时序尚需验证，不能自行假设所有等级表在地图第一帧就绪。
- `03-【一些触发传输/06-Display_ShuXing__属性加减__.lml:1550-1683` 的部分加经验分支读取玩家等级和经验、按等级查询需求经验；满足条件时更新玩家等级并用逆天运行 `hero_UP`、传入玩家，再保存余下经验。这里所看的分支是一次条件判断，跨多级的完整处理及其他入口还没有核实，不能据此承诺可一次连续升多级。
- `23-【英雄】系统+等级系统/20-hero_UP.lml:1-207` 接收玩家、读取绑定英雄与玩家等级，更新等级显示和英雄等级，读取升级相关三围、攻击、生命与护甲，并运行公共属性加减模块传入这些增量。制作类似功能时，先确认玩家状态、英雄实体、UI和属性模块的职责；不要只修改英雄等级就当作全部升级效果完成。

## 设计新练功房时的实施步骤

1. 确认玩家数量、双方归属、进出方式、矩形布局、普通怪与精英的类型和数量、成长方式、刷怪上限与失败条件；未指定时先查参考源码对应逻辑，关键规则仍不清楚时询问用户。
2. 初始化有效玩家集合、玩家和敌对玩家的对应关系、区域、怪物类型表、玩家当前刷怪等级与数量。根据现有属性系统命名并绑定必要的玩家自定义数据，不生成玩家 1/2/3 三套重复的全局变量。
3. 把事件入口、计时/数量计算、普通怪/精英创建、创建后属性处理拆为职责清楚的模块；用逆天运行触发传入玩家、类型与模式。需要通用行为时尽量一个触发服务多个玩家；不同区域与例外规则按实际保留。
4. 明确精英统计按单位类型还是单位实例、是否只算存活怪、是否包含其他类型，避免把一种标签和另一种标签混为一谈。明确英雄不在区域、玩家离开、计时器重入与目标数量变化时的行为。
5. 对单位组、点、临时单位和计时器按编辑器实际函数生命周期处理；先读回 GUI 的函数、嵌套分组、参数和状态，再由用户手动保存并进行游戏测试。此前的测试图简化方案未体现本源码的局部变量与模块化逻辑，不应作为源码复现范本。
